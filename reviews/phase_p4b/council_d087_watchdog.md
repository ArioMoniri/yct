# Council, D-087 draft (p4b_ref/v2): Watchdog review
Verdict: **REVISE.** Read: d087_draft.md, 4fa86c0, 0b0a44a, refclips58.py item_seed/LOC events, refclips_build.py manifest guard, D-071 (h), build-2 STOP_NOTE. I read no sealed data, labels, transcripts or predictions. The rule is mechanical, rank-ordered, has no tuning knob, keeps the K rules, thresholds and on_fail, and refuses to run until it is frozen. That is inside (h). Five gaps block the freeze.
## Q1-Q3
- **Q1 (face slots): agree with body+place only.** It matches the D-085 gate. The QC never gates intact-face TRs, and a face patch has a face by design, so the owner's literal "all 60" would replace all 20 faces. That is not the owner's intent. Faces are still SHINEd jointly and recorded. The owner must be told before the freeze, and the freeze row must cite the owner's answer. Note: face *scrambles* do appear on gated non-face TRs, and the screen does not cover them (see B5).
- **Q2 (C3 in v2):** MOT, MOT_STAT, FLASH and GREY_CTRL (and the NAT carry-over) must match build 1's decoded shas exactly. All 40 LOC/LOC_SCR clips are new, not just the clips with a replaced slot: SHINE is joint, so one swap changes all 60 patches. To keep them checkable, the screen record must store the sha256 of each final post-SHINE patch, and the builder must assert that its rendered patches equal those shas (B2).
- **Q3 ($0.39): accept.** Counting it against v2 is conservative and disclosed, and v1 has no further GPU spend. Wire T-DRV-V2 (`cost_cap_usd` into `guard_launch`) before any v2 GPU launch, with a test.
## Other points
- **Scramble seeds: accept.** `item_seed(LOC|LOC_SCR, i, k)` is keyed by clip and event, not by image, so the seeds are fixed before any image is seen. No re-roll is allowed.
- **TALKFACE `max_consumed_face_rank`: accept.** Under Q1 no face slot is screened, so it always equals 492. It is a harmless guard, and it amends only the unfrozen part 2. Say so in the text.
- **Continuation past 20: accept, with one condition.** The v4 logs hold only 20 passes per category, so any body or place flag forces a continuation. Appending to the v4 logs must leave rows 1..N byte-identical, and the audit must be committed before the screen re-runs. The cap of 20 extra and the snapshot STOP are fine.
- **Outcome-blindness:** a rule written after a failure is what (h) is for, and it changes stimuli only. But the draft (§7) says "place_14 is not in v2", and the rule does not guarantee that. The 0.681 hit was on the *decoded* patch, while the screen runs on the *rendered* patch (P2 YuNet passed it pre-SHINE). If the screen does not flag place_14, it stays, and it will likely fail the QC again, which is a final STOP. Any later hand exclusion would be outcome-driven. This must be fixed a priori (B1).

Write the driver and the builder's v2 path test-first, before the freeze, so the frozen rule includes that code.
4. **B4.** Owner confirmation of Q1 (and of B1/B5), recorded in DECISIONS D-087.
5. **B5 (owner question, not a silent addition).** Should the screen also run YuNet on each slot's scramble/swap patches (the seeds are known before the build)? Without it, a scramble hit after the rebuild is a final STOP. If adopted, it must be frozen now. It must never be added after a v2 result.
