## 2. BUG-020: .gitleaks.toml line allowlist for hex cache_key

**Vote: REJECT. The regex is not anchored at the start of the line, and with `regexTarget = "line"` it allowlists the whole line, so a real secret on that line is suppressed for every rule.**

Commands: gitleaks 8.21.2 (the version CI uses) in a scratch repo, run with the repo's .gitleaks.toml:
- `{"github_token": "ghp_A1b2…Q7r8", "cache_key": "0123456789abcdef",` → **not reported** (github-pat and generic-api-key both suppressed).
- `AWS_ACCESS_KEY_ID=AKIA<REDACTED-SYNTHETIC-PROBE> aws s3 ls  # "cache_key": "0123456789abcdef"` → **not reported** (aws-access-token suppressed).
- Control line without a cache_key → reported. With the allowlist removed, the leaky lines are reported again.

So any secret line that ends in a hex cache_key is silently allowed. This is realistic for minified or one-line JSON and log lines. tests/test_gitleaks_allowlist.py does not test same-line secrets, so the tests miss this.

Fix that I verified:

```toml
regexes = ['''(?m)^[+ \t]*"cache_key": "[0-9a-f]{16,64}",?[ \t]*$''']
```

- The `(?m)` is needed: in gitleaks the "line" fragment includes surrounding newlines. A plain `^…` still gave 53 findings on the repo.
- Results: full repo history 0 findings (it was 53 with no allowlist); both same-line attacks reported; adjacent-line secrets reported.
- Add the same-line attack lines to test_non_hex_or_other_keys_not_allowed. Use the `(?m)` flag in the Python mirror too (`re.M`).
